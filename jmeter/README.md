# Проверка конкурентных транзакций

Требования: JMeter 5.6.3, Java 17+, Docker Desktop. Плагины JMeter не нужны.
Команды выполняются в PowerShell из корня проекта.

## Запуск

```powershell
docker compose up -d --build --force-recreate app
# Дождаться запуска приложения на http://localhost:8080.
.\jmeter\run.ps1 -Iterations 10 -Label serializable -RetryConflicts
```

По умолчанию используется JMeter из `C:\Users\NB.PRO\Downloads\apache-jmeter-5.6.3`.
Другой путь задаётся параметром `-JMeterHome`, адрес приложения — `-BaseUrl`.
Параметр BaseUrl включает context path, если WAR развёрнут не в корне,
например `http://localhost:8080/lab1`; `/api` добавляется скриптом.

Для открытия плана в GUI с правильными путями:

```powershell
.\jmeter\run.ps1 -Gui -Iterations 1
```

В интерфейсе можно добавить `View Results Tree` или `Summary Report`.
Для нового запуска GUI лучше заново открыть план через run.ps1: так создаётся
новый идентификатор и отдельные учётные записи. Число потоков оставлять равным **2**.

## Что проверяется

Два потока JMeter входят под разными ADMIN, у каждого отдельный HttpClient и
CookieManager. Регистрация аккаунтов выполняется последовательно как подготовка.
Сами гонки синхронизируются CyclicBarrier непосредственно перед HTTP-запросами;
таймауты не дают участникам ждать бесконечно. Это барьер теста, а не блокировка
в приложении. Искусственных задержек в серверный код не добавлено.

| Сценарий | Ожидание |
|---|---|
| CRUD каждого пользователя | Создание, проверка изменения, удаление, затем GET 404 |
| Обновление / обновление | Явный конфликт 409/412 либо сохранение обоих независимых изменений |
| Обновление / удаление | Нет HTTP 500, после успешного удаления объект отсутствует и не создан заново |
| Удаление / удаление | Один 204, другой 404 или 409, объект отсутствует |
| Создание одного названия | Один 201, другой 409; ровно один объект с нормализованным названием |
| Успешный импорт | По два фильма у каждого пользователя, importedCount=2, записи доступны |
| Импорт / импорт одного названия | Один 201, другой 409; проигравший пакет не записан частично |
| Создание / импорт одного названия | Один 201, другой 409; проверка числа объектов и атомарности пакета |
| Невалидный импорт | 400, ни один фильм пакета не сохранён, есть FAILED в истории |
| Очистка | Удаление фильмов и связанных объектов текущего запуска |

Проверка update/update намеренно проверяет защиту от потери изменений. Для PUT,
который по контракту полностью заменяет объект, два 200 сами по себе не являются
нарушением SERIALIZABLE. Если второй запрос содержит устаревшие поля, для защиты
пользовательских изменений требуется версия/If-Match либо другой контракт изменения.

`-RetryConflicts` включает до четырёх попыток обычных CRUD-операций и успешного
импорта при HTTP 409 с кодом TRANSACTION_CONFLICT. Это имитация повтора клиентом;
сам backend автоматически транзакции не повторяет. В специально сталкиваемых
запросах повторов нет: исходный конфликт остаётся виден в результатах. Обычный
CRUD изменяет собственный тестовый объект, поэтому повтор PUT там не затирает
чужое пользовательское изменение. Для сравнения исходного поведения запускайте
без `-RetryConflicts`.

## Сравнение уровней изоляции

Семафор удалён. Datasource WildFly PostgresDS остаётся на READ COMMITTED.
Только MovieService.save, MovieService.update и ImportService.importMovies
повышают изоляцию своей JTA-транзакции командой
`SET TRANSACTION ISOLATION LEVEL SERIALIZABLE` до первого SQL-запроса.
Команда не меняет настройки сессии или следующих транзакций в пуле.
Чтение, удаление, авторизация и справочники уровень изоляции не повышают.
История успешного импорта записывается внутри транзакции импорта и наследует
её уровень; отдельные запросы истории и запись FAILED работают на READ COMMITTED.

MOVIE_WRITE_ISOLATION переключает только эти три операции. READ_COMMITTED —
контрольный режим без защиты; по умолчанию используется SERIALIZABLE.

```powershell
$env:MOVIE_WRITE_ISOLATION = 'READ_COMMITTED'
docker compose up -d --force-recreate app
# Дождаться готовности приложения.
.\jmeter\run.ps1 -Iterations 10 -Label read-committed

$env:MOVIE_WRITE_ISOLATION = 'SERIALIZABLE'
docker compose up -d --force-recreate app
# Дождаться готовности приложения.
.\jmeter\run.ps1 -Iterations 10 -Label serializable -RetryConflicts
```

Проверка уровня по умолчанию в пуле (READ COMMITTED в обоих режимах):

```powershell
docker compose exec -T app /opt/jboss/wildfly/bin/jboss-cli.sh --connect '--commands=/subsystem=datasources/data-source=PostgresDS:read-attribute(name=transaction-isolation,resolve-expressions=true)'
```

`SHOW default_transaction_isolation` в отдельном psql показывает настройки другой
сессии, поэтому не подтверждает изоляцию соединений приложения.
Локальное повышение задаётся первым SQL в MovieRepository.useMovieWriteIsolation;
успешные JMeter-прогоны проверяют его работу в настоящих JTA-транзакциях.

## Результаты и ограничения

В `jmeter/results/<runId>/` сохраняются:

- `report/index.html` — HTML-отчёт JMeter;
- `results.jtl` — CSV с результатами всех сценариев;
- `evidence.jsonl` — HTTP-коды, ответы, длительности отдельных запросов, инварианты и ошибки;
- `jmeter.log` — диагностический лог.

Один sample JMeter — целый сценарий, включая подготовку, барьеры и проверки.
Время в HTML-отчёте **не является задержкой одного HTTP-запроса**. Это проверка
корректности конкуренции двух пользователей, а не исследование предельной нагрузки.
При 10 итерациях должно быть 220 samples (11 этапов × 2 пользователя × 10).
Два failed samples одной парной гонки означают один провал сценария, показанный
для обоих участников. Скрипт завершает запуск кодом 1 при ошибках или неполном плане.

Фильмы, люди, координаты и локации текущего запуска очищаются через API в конце
каждой итерации. Тестовые аккаунты ADMIN и история импортов сохраняются:
в приложении нет API их удаления. При принудительном завершении или ошибке
авторизации очистка может не выполниться; завершённые прогоны проверяют её результат.
Для восстановления после такого запуска можно передать `-CleanupRunIds <runId>`
следующему запуску: будут использованы префикс и IDs из его `evidence.jsonl`.
Несколько идентификаторов разделяются запятыми. Чужие объекты по этому параметру
не выбираются; файл доказательств должен сохраниться в `results/<runId>/`.
Не запускайте сценарий на рабочей базе. Отсутствие дублей в серии из 10 повторов
само по себе не доказывает корректность для всех возможных расписаний.

Результаты проведённых экспериментов и вывод для отчёта — в `REPORT.md`.
