# Исследование локального повышения изоляции

Дата: 27 октября 2026 года, Europe/Moscow.

## Что изменено

Глобальный SERIALIZABLE отменён. Пул PostgresDS использует READ COMMITTED.
Семафора и явных блокировок в приложении нет.

Только следующие методы повышают изоляцию своей текущей JTA-транзакции:

| Метод | Почему требуется SERIALIZABLE |
|---|---|
| MovieService.save | Проверка свободного названия и создание фильма должны быть согласованы с другими записями |
| MovieService.update | Переименование также может конфликтовать с созданием, импортом или другим переименованием |
| ImportService.importMovies | Проверка всех названий и сохранение всего пакета должны быть одной согласованной операцией |

Повышение выполняет MovieRepository.useMovieWriteIsolation командой
`SET TRANSACTION ISOLATION LEVEL SERIALIZABLE`. В save/update это первый шаг
метода, причём в update он расположен **до** findById. При импорте команда
выполняется после проверки входных данных в памяти, до первого чтения из БД.

Команда меняет только текущую транзакцию. После commit или rollback следующие
транзакции на том же соединении снова используют READ COMMITTED. Настройки
соединения через setTransactionIsolation и SET SESSION не меняются.
Это соответствует [документации PostgreSQL SET TRANSACTION](https://www.postgresql.org/docs/15/sql-set-transaction.html):
команду необходимо выполнить до первого чтения или изменения данных.

Следующие операции изоляцию не повышают: чтение фильмов, удаление, авторизация,
регистрация, отдельные операции справочников, чтение истории и запись FAILED.
Сохранение вложенных объектов и SUCCESS в истории при успешном импорте входит
в его общую атомарную транзакцию и потому наследует её SERIALIZABLE.

Удаление не создаёт и не переименовывает фильмы, поэтому для защиты уникальности
SERIALIZABLE ему не нужен. Конкурентное удаление обрабатывается как отсутствие
объекта или HTTP 409. Чтения не участвуют в последовательности «проверить и записать».

TransactionConflictMapper сохранён: ошибки сериализации и конкурентного
изменения возвращают HTTP 409 TRANSACTION_CONFLICT вместо HTTP 500.
Автоматических повторов транзакций на сервере нет.

## Как проверялось

На одном и том же коде выполнены два JMeter-прогона: два ADMIN с независимыми
сессиями, 10 итераций, 220 samples в каждом прогоне. Пул в обоих случаях оставался
на READ COMMITTED. Переменная MOVIE_WRITE_ISOLATION меняла только поведение трёх
перечисленных методов: READ_COMMITTED отключает локальное повышение для
контрольного эксперимента, SERIALIZABLE включает его и используется по умолчанию.

В обоих запусках включён -RetryConflicts для обычных операций с собственными
тестовыми объектами. В намеренно сталкиваемых запросах повторов нет.
После гонки проверяются ответы и итоговое состояние объектов через API.

Management CLI WildFly подтвердил `TRANSACTION_READ_COMMITTED` для PostgresDS
при включённом MOVIE_WRITE_ISOLATION=SERIALIZABLE. Проверка CLI показывает уровень
пула, а не временное повышение внутри отдельного метода.

В обоих режимах прошли обычный CRUD, успешный импорт, невалидный импорт,
проверки истории и очистка. При локальном SERIALIZABLE также прошли проверки
атомарности проигравшего пакета в конфликтующих импортах.

Без локального повышения: 142 успешных samples из 220, 78 failed.
С локальным повышением: 212 успешных samples из 220, 8 failed.
Восемь failed относятся к четырём парам устаревших PUT: результат общей
проверки показывается для обоих участников. Эти ошибки оставлены видимыми.

## Вывод и оставшееся ограничение

Для гонки «прочитать названия — проверить — сохранить» READ COMMITTED недостаточно:
оба пользователя могут проверить название до фиксации конкурирующей записи.
Локальный SERIALIZABLE устраняет наблюдавшиеся дубли, откатывая конфликтующую
транзакцию. Повышать изоляцию авторизации, справочников или обычного чтения
для этого не требуется. Все пути создания и переименования должны соблюдать
одну и ту же транзакционную границу.

Устаревший полный PUT — отдельная проблема. Например, оба пользователя читают
budget=100, length=90. Один отправляет 101/90, другой 100/91. Если транзакции
выполнились последовательно, второй PUT может затереть бюджет первого и
получить 200 даже при SERIALIZABLE. Это допустимо с точки зрения сериализуемости.
Для защиты пользовательских изменений нужна проверка версии клиента, например
version/If-Match, либо другой контракт обновления. В этом изменении она не добавлялась.

Из-за чтения всего списка названий SERIALIZABLE может конфликтовать и при
записи разных фильмов. Клиент должен обрабатывать 409 и повторять операцию
после обновления данных. Десять повторов демонстрируют наблюдавшееся поведение,
но не покрывают все возможные расписания транзакций.
