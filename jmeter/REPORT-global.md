# Архив: эксперимент с глобальным SERIALIZABLE

Это исторический эксперимент. Глобальное повышение изоляции отменено.
Текущая реализация повышает изоляцию только для создания, обновления и импорта
фильмов. Актуальные результаты находятся в REPORT.md.

Дата: 27 октября 2026 года, Europe/Moscow.

## Изменение реализации

Из MovieNameService удалены Semaphore, ожидание блокировки и обработчик
JTA afterCompletion. Осталась обычная проверка: прочитать существующие названия,
нормализовать их в Java, проверить новое название и сохранить фильм в той же
JTA-транзакции. Проверка внутри импортируемого пакета также сохранена.
Явных блокировок приложения и SELECT FOR UPDATE не добавлено.

Для datasource WildFly PostgresDS задан уровень TRANSACTION_SERIALIZABLE.
Он переключается переменной TRANSACTION_ISOLATION в docker-compose.yml.
Параметр установлен в datasource, поскольку соединениями управляет JTA-пул.
Семафор не включается ни в одном из сравнительных режимов.

Добавлен TransactionConflictMapper: SQLSTATE 40001 (ошибка сериализации),
40P01 (deadlock) и Hibernate StaleStateException возвращаются клиенту как
HTTP 409 с кодом TRANSACTION_CONFLICT. При поиске причины учитываются cause,
suppressed и SQLException.nextException. Другие ошибки не выдаются за конфликт.
Автоматического повторения транзакций на сервере нет.

## Методика

Использованы Apache JMeter 5.6.3, PostgreSQL 15 и WildFly 36, приложение собрано
из текущего проекта. Два потока JMeter используют разные учётные записи ADMIN
и независимые cookie-сессии. В каждом режиме выполнено 10 итераций, 220 samples.
Парные запросы синхронизируются барьером на стороне теста. Проверяются как
HTTP-ответы, так и сохранённое состояние через последующие GET-запросы.

Для окончательного сравнения использованы одинаковые код приложения,
обработчик конфликтов и сценарии. Менялся только уровень изоляции datasource.
В обоих запусках включён -RetryConflicts: клиент может повторять обычные
операции при TRANSACTION_CONFLICT; в намеренно сталкиваемых запросах повторов нет.
Регистрация аккаунтов выполняется последовательно и не входит в проверяемые гонки.

Применённое значение проверялось через management CLI WildFly:

```text
/subsystem=datasources/data-source=PostgresDS:read-attribute(name=transaction-isolation,resolve-expressions=true)
```

До эксперимента в movie был только первичный уникальный индекс по id.
Уникального индекса по названию нет; при исследовании он не добавлялся.

На обоих уровнях прошли обычный CRUD, успешный импорт, проверка невалидного
пакета и истории, а также очистка тестовых объектов во всех 10 итерациях.
На SERIALIZABLE дополнительно прошли проверки отсутствия частично записанного
проигравшего пакета при конкурентных импортах и при гонке создания с импортом.

READ COMMITTED: 156 успешных samples из 220, 64 failed.
SERIALIZABLE: 218 успешных samples из 220, 2 failed.
Два failed samples на SERIALIZABLE относятся к одной паре update/update
в десятой итерации: оба участника получают результат общей проверки.
План намеренно не маскирует этот оставшийся дефект зелёным результатом.

## Объяснение

При READ COMMITTED два запроса могут прочитать набор названий до фиксации
друг друга. Оба решают, что название свободно, и сохраняют разные строки с
одинаковым нормализованным названием. Проверка уникальности в Java сама по себе
не делает последовательность «проверить и записать» атомарной между транзакциями.

SERIALIZABLE отслеживает зависимости чтения и записи. Если совместная фиксация
транзакций дала бы результат, невозможный при их последовательном выполнении,
PostgreSQL откатывает одну из них. Поэтому один запрос проходит, а другой
получает конфликт. Если второй запрос начинает проверку уже после фиксации
первого, дубликат отклоняет сама проверка MovieNameService.

Промежуточный эксперимент без TransactionConflictMapper показал: повышение
изоляции уже предотвращает дубли, но отклонённые транзакции выходят наружу как
HTTP 500. Следовательно, повышение уровня изоляции должно сопровождаться
обработкой конфликтов. В окончательном варианте возвращается HTTP 409.

## Оставшееся ограничение обновления

У Movie нет версии, а PUT передаёт полное состояние объекта.
Исходно budget=100 и length=90. Первый пользователь отправляет budget=101,
length=90; второй — budget=100, length=91. В окончательном прогоне оба получили
200, но итоговое состояние было budget=100, length=91: изменение бюджета потерялось.

Это возможно и при последовательном выполнении транзакций: второй PUT содержит
устаревшее значение бюджета. Поэтому SERIALIZABLE не обязан отклонять такую
последовательность. Для полного предотвращения потери пользовательских изменений
понадобится версия объекта и проверка версии клиента (например, If-Match) либо
контракт обновления отдельных полей. Эти изменения в данном эксперименте не вносились.

Для отчёта нельзя утверждать, что SERIALIZABLE устранил все проблемы конкуренции.
Он устранил наблюдавшуюся гонку проверки уникальности и обеспечивает сериализуемость
зафиксированных транзакций; отдельная защита устаревших пользовательских форм остаётся
необходимой.

## Цена решения и область применения

Настройка применяется ко всему PostgresDS: это намеренно простой вариант для
лабораторной. Возможны конфликты и у операций с разными объектами, особенно потому,
что проверка названия читает весь набор фильмов. Клиенту нужно обновлять данные и
повторять отклонённую операцию; HTTP 409 не означает успешное сохранение.
Все пути записи фильмов должны выполнять проверку и запись в одной транзакции
с этим уровнем изоляции. Прямая запись в БД в обход проверки им не защищается.

Десять повторов демонстрируют воспроизведённое поведение, но не покрывают все
возможные расписания. Измеренное время JMeter включает подготовку сценария,
синхронизацию и проверку результата, поэтому не используется здесь как метрика
задержки одного запроса или предельной производительности.

Основание для интерпретации: [PostgreSQL 15 — Transaction Isolation](https://www.postgresql.org/docs/15/transaction-iso.html),
разделы Read Committed и Serializable. PostgreSQL требует быть готовым к откату
и повторению конфликтующих SERIALIZABLE-транзакций.
