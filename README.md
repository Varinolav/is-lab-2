# Исследование конкурентного доступа и изоляции транзакций

Лабораторная работа посвящена проверке информационной системы учёта фильмов
при одновременной работе нескольких пользователей. Для экспериментов используется
Apache JMeter. Проверяется не только получение HTTP-ответов, но и итоговое
состояние объектов после конкурентных операций.

## Задача и покрытие требований

| Требование | Реализация |
|---|---|
| Одновременная работа нескольких пользователей | Два администратора с независимыми HTTP-сессиями |
| Создание, редактирование и удаление объектов | Сценарий CRUD для каждого пользователя |
| Импорт объектов | Успешные и невалидные пакеты, проверка истории и атомарности |
| Работа с одним объектом из нескольких сессий | Обновление/обновление, обновление/удаление, удаление/удаление |
| Проверка уникальности при конкурентном создании | Создание/создание, импорт/импорт, создание/импорт одного названия |
| Исследование и изменение изоляции | Сравнение READ COMMITTED с локальным SERIALIZABLE для операций записи фильмов |
| Обоснование изменений | Результаты экспериментов и объяснение приведены ниже |

Все перечисленные сценарии реализованы. Защита уникальности проверена;
оставшееся ограничение обновления устаревшим полным PUT описано отдельно.

## Проверяемое ограничение предметной области

Название фильма должно быть уникальным без учёта регистра и пробельных символов
по краям. Перед сравнением применяется `strip().toLowerCase(Locale.ROOT)`.
Например, `Дюна`, `ДЮНА` и ` Дюна ` считаются одним названием.

Проверка выполняется в бизнес-логике приложения, в `MovieNameService`.
Уникальный индекс, триггер или дополнительное ограничение БД по названию
не добавлялись. Для импорта проверяются также повторы внутри самого пакета.
При редактировании текущий фильм исключается из проверки собственного названия.

## Транзакции и выбор изоляции

При READ COMMITTED два запроса могут одновременно прочитать список названий,
не увидеть ещё не зафиксированные изменения друг друга и оба сохранить фильм
с одним названием. Поэтому проверка и запись должны выполняться внутри
транзакций с более строгой изоляцией.

Пул соединений `PostgresDS` оставлен на **READ COMMITTED**. Изоляция повышается
до **SERIALIZABLE** только в следующих операциях:

| Метод | Причина |
|---|---|
| `MovieService.save` | Проверка названия и создание фильма |
| `MovieService.update` | Проверка названия при изменении, в том числе при переименовании |
| `ImportService.importMovies` | Проверка названий и атомарное сохранение всего пакета |

Перед первым SQL-запросом этих операций выполняется
`SET TRANSACTION ISOLATION LEVEL SERIALIZABLE` через текущую Hibernate-сессию.
Это меняет только текущую JTA-транзакцию. После её завершения повышение
не переносится на следующие транзакции соединения из пула.

Используется `jakarta.transaction.Transactional`, у которой нет параметра
`isolation`, поэтому локальная установка изоляции реализована отдельно.
Семафор и явные блокировки приложения не используются.

Чтение фильмов, удаление, авторизация, регистрация и отдельные операции
справочников работают на READ COMMITTED. Сохранение вложенных объектов и записи
SUCCESS в истории является частью транзакции успешного импорта и наследует
её уровень изоляции. Чтение истории и отдельная запись FAILED изоляцию не повышают.

При конфликте сериализации PostgreSQL откатывает одну из транзакций.
`TransactionConflictMapper` преобразует такой конфликт в HTTP **409** с кодом
`TRANSACTION_CONFLICT`. Клиенту требуется обновить данные и повторить операцию.
Сам сервер автоматически транзакции не повторяет.

## Запуск приложения

Требуются запущенный Docker Desktop, Java 17+ и установленный JMeter 5.6.3.
Следующие команды предназначены для PowerShell из корня проекта.

```powershell
$env:MOVIE_WRITE_ISOLATION = 'SERIALIZABLE'
docker compose up -d --build --force-recreate app
```

Дождаться готовности приложения по адресу [http://localhost:8080](http://localhost:8080).
Режим SERIALIZABLE используется по умолчанию; переменная задаётся явно для
воспроизводимости демонстрации. Она управляет только тремя операциями записи
фильмов и не меняет изоляцию всего пула.

## Демонстрация в GUI JMeter

Открыть подготовленный план через скрипт:

```powershell
.\jmeter\run.ps1 -Gui -Iterations 10 -Label demonstration -RetryConflicts
```

По умолчанию скрипт использует JMeter из
`C:\Users\NB.PRO\Downloads\apache-jmeter-5.6.3`. Для другого расположения:

```powershell
.\jmeter\run.ps1 -Gui -Iterations 10 -RetryConflicts -JMeterHome 'C:\tools\apache-jmeter-5.6.3'
```

Скрипт передаёт пути к Groovy-файлу, адрес приложения и новый идентификатор запуска.
Это позволяет открыть план без ручного исправления путей в JMeter.

1. В дереве плана выбрать группу **Two administrators (keep exactly 2 threads)**.
2. Через контекстное меню добавить **Add → Listener → View Results Tree**.
3. Аналогично добавить **Add → Listener → Summary Report**.
4. Оставить **Number of Threads = 2**. Число повторов задаётся параметром
   `-Iterations`; его можно изменить и в поле **Loop Count** группы.
5. Запустить план кнопкой **Start** или сочетанием **Ctrl+R**.
6. Дождаться завершения обоих потоков и просмотреть результаты в listeners.

Для нового независимого эксперимента закрыть JMeter и снова открыть его через
`run.ps1`: будет создан новый идентификатор и новые тестовые аккаунты.
HTML-отчёт автоматически создаётся при запуске в CLI, описанном ниже;
в GUI результаты просматриваются в добавленных listeners.

### Состав плана

| № | Сценарий | Что проверяется |
|---:|---|---|
| 01 | Подготовка | Регистрация двух ADMIN, вход в разные сессии, создание связанных объектов |
| 02 | CRUD | Создание, редактирование, чтение результата, удаление и последующий GET 404 |
| 03 | Обновление / обновление | Два пользователя меняют разные поля одного исходного объекта; проверяется потеря изменений |
| 04 | Обновление / удаление | Нет HTTP 500, после успешного удаления объект отсутствует и не создаётся заново |
| 05 | Удаление / удаление | Один ответ 204, другой 404 или 409; объект отсутствует |
| 06 | Создание / создание | Один ответ 201, другой 409; нормализованное название встречается ровно один раз |
| 07 | Успешный импорт | По два фильма для каждого пользователя, importedCount=2, записи доступны |
| 08 | Импорт / импорт | Конфликт одинакового названия и отсутствие частичной записи проигравшего пакета |
| 09 | Создание / импорт | Уникальность названия между разными способами записи и атомарность импорта |
| 10 | Невалидный импорт | Ответ 400, фильмы пакета не сохранены, история содержит SUCCESS и FAILED |
| 11 | Очистка | Удаление созданных текущим запуском фильмов и связанных объектов |

Аккаунты регистрируются последовательно как подготовительный этап.
Для намеренно конкурентных запросов используется барьер на стороне JMeter.
Он синхронизирует начало запросов, но не блокирует транзакции приложения.

Параметр `-RetryConflicts` разрешает до четырёх попыток обычных операций
с собственными тестовыми объектами при HTTP 409 TRANSACTION_CONFLICT.
В специально сталкиваемых запросах повторов нет: их первоначальные ответы
сохраняются для анализа.

Один результат JMeter соответствует целому сценарию, включая подготовку,
барьеры и проверки. Его код 200 означает, что проверки сценария прошли;
HTTP-коды отдельных запросов записываются в `evidence.jsonl`.
Поэтому время sample нельзя считать задержкой одного HTTP-запроса.

## Воспроизведение гонки и сравнение режимов

### Контрольный режим: READ COMMITTED

Отключить локальное повышение изоляции и пересоздать контейнер приложения:

```powershell
$env:MOVIE_WRITE_ISOLATION = 'READ_COMMITTED'
docker compose up -d --force-recreate app
```

После готовности приложения открыть новый экземпляр JMeter:

```powershell
.\jmeter\run.ps1 -Gui -Iterations 10 -Label read-committed -RetryConflicts
```

Запустить план. В сценариях **06**, **08** и **09** гонка проявляется как два
ответа 201 и два фильма с одним нормализованным названием. Проверка сценария
в таком случае завершается ошибкой. Частота проявления зависит от расписания запросов.

### Защищённый режим: локальный SERIALIZABLE

```powershell
$env:MOVIE_WRITE_ISOLATION = 'SERIALIZABLE'
docker compose up -d --force-recreate app
```

После готовности приложения открыть новый запуск:

```powershell
.\jmeter\run.ps1 -Gui -Iterations 10 -Label local-serializable -RetryConflicts
```

В сценариях уникальности ожидаются один ответ 201, один 409 и ровно один
сохранённый фильм. Пул соединений остаётся на READ COMMITTED в обоих режимах.
После демонстрации оставить включённым SERIALIZABLE для операций записи фильмов.

## Полученные результаты

Эксперимент выполнен 27 октября 2026 года. В каждом режиме работали два
администратора, выполнено 10 итераций, по 220 samples. Использовались одинаковые
код приложения и тестовый план; менялся только режим локального повышения.

В таблице учитываются 10 парных попыток каждого сценария.

| Наблюдение | READ COMMITTED | Локальный SERIALIZABLE |
|---|---:|---:|
| Дубли при создании одного названия | 10/10 | 0/10 |
| Дубли при импорте одного названия | 10/10 | 0/10 |
| Дубли при создании одновременно с импортом | 9/10 | 0/10 |
| Корректное обновление одновременно с удалением | 10/10 | 10/10 |
| Корректное двойное удаление | 10/10 | 10/10 |
| Потеря изменений при устаревших полных PUT | 10/10 | 4/10 |
| HTTP 500 во всём прогоне | 0 | 0 |

С локальным SERIALIZABLE все 10 попыток каждого сценария уникальности завершились
парой ответов 201/409. Успешные импорты и проверки атомарности проигравших пакетов
прошли. Обычный CRUD, невалидный импорт, история и очистка прошли в обоих режимах.

- READ COMMITTED: 142 успешных samples, 78 failed.
- Локальный SERIALIZABLE: 212 успешных samples, 8 failed.

Восемь failed во втором режиме относятся к четырём парам устаревших PUT.
Общая ошибка парной проверки показывается для обоих пользователей, поэтому
два failed samples не означают два независимых случая.

Все **24 Java-теста** прошли. В том числе проверены порядок установки изоляции
до первого чтения и отсутствие её повышения в методах чтения и удаления.

## Оставшееся ограничение: устаревший полный PUT

Исходный фильм имеет `budget=100`, `length=90`.
Первый пользователь отправляет `budget=101`, `length=90`, а второй —
`budget=100`, `length=91`. Оба запроса могут получить 200, но итоговое состояние
будет `100/91` или `101/90`: одно изменение затёрто устаревшим полем второго PUT.

Такой результат возможен даже при последовательном выполнении транзакций,
поэтому SERIALIZABLE не гарантирует предотвращение этой потери пользовательских
изменений. Для неё необходима проверка версии, например version/If-Match,
либо иной контракт изменения отдельных полей. Эта защита пока не реализована.

В GUI проблема обнаруживается в сценарии **03 Concurrent update-update
(detect lost updates)**: в **Sampler result** или **Response data** появляется
сообщение `LOST UPDATE`. Если проблема не проявилась за 10 повторов, можно
выполнить 30 повторов. Точное число ошибок между запусками может отличаться.

Таким образом, сценарий проверки реализован, однако считать все проблемы
конкурентного редактирования исправленными нельзя. Повышение изоляции решило
наблюдавшуюся гонку проверки уникальности; устаревшие пользовательские изменения
требуют отдельного решения.

## Вывод

При READ COMMITTED проверка уникальности названия в Java не предотвращает
одновременную успешную запись двух фильмов с одним названием. Для создания,
изменения и импорта фильмов изоляция повышена локально до SERIALIZABLE:
проверка названий и сохранение выполняются в одной транзакции, а конкурирующая
несогласованная запись отклоняется с HTTP 409.

Повышать изоляцию всех транзакций приложения для этой задачи не требуется.
Цена выбранного решения — возможные конфликты и необходимость повторения
отклонённых операций. Поскольку проверка читает весь список названий,
конфликтовать могут и записи разных фильмов.

Отсутствие дублей в проведённой серии подтверждает наблюдавшееся поведение,
но не заменяет анализа всех путей записи. Это исследование корректности
конкурентных операций, а не измерение предельной производительности системы.

## Примечания к данным эксперимента

Тестовые фильмы и связанные объекты очищаются в конце каждой итерации.
Аккаунты администраторов и история импортов сохраняются, поскольку в приложении
нет API их удаления. При принудительном завершении очистка может не выполниться;
восстановление по сохранённым доказательствам описано в `jmeter/README.md`.
Для эксперимента следует использовать тестовую базу.
